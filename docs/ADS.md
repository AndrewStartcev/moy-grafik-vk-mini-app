# Advertising policy

## Цель

Монетизировать полезный сервис рекламой, не разрушая retention.

## Принципы

1. Пользователь сначала получает ценность, потом видит рекламу.
2. Ошибка или недоступность рекламы никогда не ломает приложение.
3. Все рекламные вызовы идут через `src/services/ads.ts`.
4. Компоненты не вызывают VK Bridge advertising methods напрямую.
5. Переключение месяца, открытие даты и базовая навигация не являются рекламными триггерами.
6. Пока рекламный кабинет находится на проверке, приложение должно работать идентично — проверки доступности просто возвращают отсутствие рекламы.

## Реализованные форматы

### Sticky/banner

Используется только на основном экране календаря.

Последовательность:

```text
supports VKWebAppCheckBannerAd?
↓
VKWebAppCheckBannerAd
↓
available?
↓
VKWebAppShowBannerAd
```

Параметры placement:

- `banner_location: bottom`;
- `banner_align: center`;
- `layout_type: resize`;
- `can_close: true`.

Правила:

- onboarding без рекламы;
- настройки без рекламы;
- баннер не вставляется внутрь календаря;
- баннер скрывается при размонтировании календаря;
- недоступный placement не создаёт alert/error screen.

### Interstitial

Последовательность:

```text
supports VKWebAppCheckNativeAds?
↓
frequency cap
↓
VKWebAppCheckNativeAds({ ad_format: interstitial })
↓
available?
↓
VKWebAppShowNativeAds({ ad_format: interstitial })
```

Текущая политика frequency cap:

- первые 3 открытия приложения — без interstitial;
- первый возможный показ — с 4-го открытия;
- максимум один interstitial за текущую JS-сессию;
- cooldown между успешными показами — 6 часов;
- счётчик не увеличивается при переходе календарь → настройки → календарь внутри одной сессии.

## Запрещённые триггеры

Interstitial не показывается:

- сразу после первого запуска;
- сразу после `Построить график` как награда/штраф за создание графика;
- при каждом переходе месяца;
- при каждом открытии дня;
- при сохранении override;
- на экране ошибки;
- при сбросе данных;
- во время системного диалога/пикера.

## Failure behavior

Любой ad call работает по принципу:

```text
supports?
↓
available?
↓
show
↓
track result
↓
return control to product
```

При ошибке:

- фиксируется `ad_failed`;
- blocking alert не показывается;
- пользователь продолжает работать с календарём.

## События

Текущие события:

- `ad_request`;
- `ad_shown`;
- `ad_failed`;
- payload `format: banner | interstitial`.

Персональные данные в advertising analytics не записываются.

## Рекламный кабинет

Код рекламы уже находится в production branch. Отдельной сборки без рекламы не требуется.

Пока кабинет VK находится на проверке, `Check*Ad`/availability могут возвращать недоступность — это штатный сценарий и не требует изменения кода.

После одобрения кабинета нужно проверить реальные показы на тестовом/опубликованном приложении и только после этого менять frequency cap.

## После релиза

Решение об увеличении частоты рекламы принимается только совместно с retention-метриками.

Если рост показов ухудшает D1/D7 или sessions/user — frequency cap откатывается.
