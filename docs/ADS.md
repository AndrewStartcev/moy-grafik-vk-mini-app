# Advertising policy

## Цель

Монетизировать полезный сервис рекламой, не разрушая retention.

## Принципы

1. Пользователь сначала получает ценность, потом видит рекламу.
2. Ошибка рекламного SDK никогда не ломает приложение.
3. Все рекламные вызовы идут через `AdService`.
4. Частота interstitial ограничена централизованно.
5. Переключение месяца, открытие даты и базовая навигация не являются рекламными триггерами.

## MVP formats

### Sticky/banner

Разрешён после создания первого графика.

Требования:

- не показывать в onboarding;
- не перекрывать CTA;
- учитывать safe area;
- не вставлять внутрь сетки календаря;
- скрывать, если placement недоступен.

### Interstitial

MVP подключает только при подтверждённой доступности текущего VK API.

Первичная политика frequency cap:

- не на первом запуске;
- не раньше нескольких полноценных повторных использований;
- не более одного показа за сессию;
- локальный cooldown между показами;
- конкретные значения вынести в конфигурацию, а не хардкодить в компоненты.

До получения реальных метрик не оптимизировать приложение под максимальное число показов.

## Запрещённые триггеры

Interstitial нельзя показывать:

- сразу при открытии приложения;
- сразу после `Построить график`;
- при каждом переходе месяца;
- при каждом открытии дня;
- при сохранении override;
- на экране ошибки;
- при сбросе данных;
- во время системного диалога/пикера.

## Failure behavior

Любой ad call:

```text
try
↓
available? → show
↓
track result
↓
return control to product
```

При ошибке:

- записать техническое событие;
- не показывать blocking alert;
- продолжить работу приложения.

## Метрики

Минимум:

- ad_request;
- ad_available;
- ad_unavailable;
- ad_shown;
- ad_closed;
- ad_failed;
- format;
- placement;

Не включать персональные данные.

## После релиза

Решение об увеличении частоты рекламы принимается только совместно с D1/D7 и sessions/user.

Если рост показов ухудшает retention — откатываем frequency cap.
